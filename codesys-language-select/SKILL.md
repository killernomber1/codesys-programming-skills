# 编程语言选择原则

## R — 原文（Reading）

> 没有哪种编程语言是绝对的好或不好，不同的工程应用具有不同的最佳编程方式。
>
> 在实际的工程项目中，涉及算法部分请选择 ST 语言；涉及流程控制部分请选择 SFC 语言；涉及逻辑控制部分请选择 LD 语言；涉及功能块部分请选择 CFC 或者 FBD。
>
> — 陆国君

---

## I — 方法论骨架（Interpretation）

六种 IEC 61131-3 编程语言（CODESYS 增加 CFC 为第六种）没有绝对的优劣之分，每种语言在特定场景下具有显著优势。**关键不是掌握所有语言，而是在正确场景使用正确的语言。**

### 快速决策树

```
┌─ 算法/数学运算/数据处理? ───> ST
│
┌─ 顺序控制/工序/状态机? ──> SFC
│
├─ 逻辑联锁/互锁/启停? ──> LD
│
├─ 功能块组态/信号链? ──> FBD 或 CFC
│   ├─ 简单信号链 ──> FBD
│   └─ 大规模连续控制/自定义顺序 ──> CFC
│
└─ 底层操作/V2兼容? ──> IL（现代工程避免使用）
```

### 实用建议总结

| 场景 | 最佳语言 | 选择理由 |
|------|----------|----------|
| 复杂数学运算、PID 计算、数据滤波 | **ST** | 文本化、运算符丰富、适合高级算法 |
| 配方管理、数据统计与分析 | **ST** | 数组/循环/条件结构处理能力强 |
| 多阶段工序、批处理、流水线 | **SFC** | 步-转移模型天然匹配顺序逻辑 |
| 交通灯、安检流程、启动/停止序列 | **SFC** | 状态可视化，故障定位直观 |
| 电机正反转、阀门联锁、急停逻辑 | **LD** | 电气工程师直观理解，梯形图传统优势 |
| 安全联锁、"3取2"表决逻辑 | **LD** | 触点-线圈模型易读易维护 |
| 模拟量信号处理链、I/O 映射 | **FBD** | 图形化功能块连线直观 |
| 多轴同步、驱动器控制、复杂反馈回路 | **CFC** | 自由放置+数据流排序，反馈路径支持 |
| 计数器/定时器组合逻辑 | **LD/FBD** | 标准库功能块拖拽即用 |

### 核心原则
- **语言无优劣，场景定胜负**：不迷信某一种语言，根据不同逻辑类型选择最适合的语言
- **模块内统一，项目内混合**：一个 POU 内只用一种语言，不同 POU 可以使用不同的语言
- **人员因素**：考虑团队技能构成，电气背景团队适合 LD，软件背景团队适合 ST

## A1 — 书中的应用（Past Application）

### 案例 1: 交通灯信号控制 — SFC 做主 + ST 做算法 + IL 做延时
- **问题**: 交通灯需要多阶段按序切换，但切换逻辑中也有信号分配算法和计数器统计，单一语言难以兼顾可读性和灵活性。
- **语言选择**: 主程序用 **SFC** 构建 5 个状态的状态机（Init -> Switch1 -> Green2 -> Switch2 -> Green1 循环），信号分配算法封装为功能块用 **ST**（CASE 语句），延时控制用 **IL**。
- **结果**: SFC 让流程控制一目了然，ST 让算法简洁高效，语言各取所长。

### 案例 2: 停车场管理 — CFC 数据流驱动 vs 其他语言
- **问题**: 停车场系统需要处理入口/出口计数、闸机时序、满位判断，功能块之间具有明确的信号传递关系。
- **语言选择**: 如果强调功能块连线与信号流清晰可见，选 **CFC**；如果团队更熟悉梯形图且逻辑简单，也可用 **LD** 配合计数器功能块。
- **结果**: CFC 版在调试时信号处理链一目了然；LD 版在维护交接时更易被电气人员理解。两种选择在原则上是"场景决定"的最佳体现。

### 案例 3: 恒压变频供水 — LD 大型工程
- **问题**: 恒压供水系统涉及手动/自动切换、PID 闭环、工频/变频切换、多泵联锁，逻辑复杂但以开关量和联锁为主。
- **语言选择**: 全书选择了 **LD**。因为主要逻辑是条件联锁（变频器上限到达切工频、频率下限到达切第二台泵等），LD 梯形图直观表达触点-线圈关系更符合逻辑联锁的本质。
- **结果**: 使用 LD 完成了数百行的工频/变频切换逻辑，如果换成 ST 反而会降低可读性。

### 用户会在什么情境下需要这个 skill?

1. 开始一个全新的 CODESYS 项目，不确定该用哪种语言作为主编程语言

## E — 可执行步骤（Execution）

1. **分析模块逻辑类型**
   - 列出该模块/程序段的主要逻辑特征：
     - 数学运算/数据处理/算法 -> 推荐 **ST**
     - 顺序控制/多阶段工序 -> 推荐 **SFC**
     - 开关量联锁/互锁/安全逻辑 -> 推荐 **LD**
     - 功能块数据流/信号处理链 -> 推荐 **FBD** 或 **CFC**
   - 完成标准：确定了模块的逻辑类型归属

2. **考虑团队和环境因素**
   - 项目维护人员的技能背景？
     - 电气/自动化背景偏多 -> 优先 LD、FBD
     - 软件/计算机背景偏多 -> 优先 ST、CFC
   - 项目是否需要跨平台移植？
     - ST 移植性最好，所有 IEC 61131-3 平台都支持
     - LD/FBD 移植性次之
     - CFC 是 CODESYS 特有，移植受限
   - 完成标准：语言选择考虑了团队技能和平台兼容性

3. **模块划分与语言分配**
   - 将大程序按功能拆分为多个 POU
   - 每个 POU 选择最适合其逻辑类型的语言
   - 示例：PRG_TrafficMain（SFC） + FB_SignalAssign（ST） + FB_WaitControl（LD）
   - 完成标准：模块划分完成，每个 POU 分配了语言，无"一个 POU 内混用多种语言"的情况

4. **验证选型合理性**
   - 反问：如果换成另一种语言，可读性会更好还是更差？
   - 反问：如果换成另一种语言，代码量会显著增加还是减少？
   - 反问：团队中是否有人不能理解这种语言？
   - 完成标准：对每个 POU 的语言选择有充分理由，通过至少两个"反问"测试

## B — 边界（Boundary）★

### 不要在以下情况使用此 skill
- 用户已经确定语言，只需要具体语法（IF/CASE/FOR 怎么写），应使用 **codesys-st-language** skill
- 用户需要的是 CFC 的详细执行顺序配置（拓扑排序 vs 数据流排序的操作步骤），该内容在 **codesys-st-language** skill 中作为补充
- 用户询问变量声明（VAR_INPUT/VAR_OUTPUT）或匈牙利命名法，应使用 **codesys-variable-system** skill
- 用户询问 POU 类型选择（FUN/FB/PRG 的区别和选择），应使用 **codesys-pou-design** skill
- 用户询问任务配置（循环周期/优先级/看门狗），不使用此 skill
- 本 skill 只给出"选哪种语言"的决策，不涉及具体语言语法
