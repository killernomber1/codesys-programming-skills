# POU 分层设计模式（FUN / FB / PRG）

## R — 原文（Reading）

> 程序组织单元（Program Organization Unit, POU）由声明区和代码区两部分组成，是用户程序的最小软件单元。按功能分可分为函数（FUN）、功能块（FB）和程序（PRG）。
>
> 函数只能调用函数，不能调用功能块。
>
> 功能块调用在调用功能块实例前，首先需要对该功能块进行实例化。
>
> 每种数据的命名总以它相对应的前缀开始，如程序用 PRG_ 开始，功能块用 FB_ 前缀开始，函数用 FC_ 或 FUN_ 前缀开始，全局变量列表用 GlobVar 前缀开始。
>
> 可以将您的工程按工艺或功能分成几段程序。在主程序中进行调用。需要反复调用的程序段可以建成功能块。个别的算法程序可以建成函数。
>
> — 陆国君

## I — 方法论骨架（Interpretation）

将 IEC 61131-3 的 POU 体系理解为一个三层架构，每层有明确的角色、生命周期和调用约束：

1. **函数（FUN）** — 无状态算法单元。给定相同输入必得相同输出，不保留内部状态，无需实例化。适合纯数学运算、数据转换、类型转换等场景。**调用约束：FUN 只能调用 FUN**，不能调用 FB 或 PRG。

2. **功能块（FB）** — 有状态组件。需要实例化后才能使用，每个实例独立维护内部数据和状态（类似 OOP 的"类-对象"关系）。适合封装有记忆功能的逻辑：定时器、计数器、PID 调节、电机控制等。**调用约束：FB 可调用 FUN 和 FB**，但不能调用 PRG。

3. **程序（PRG）** — 顶层入口。通过任务配置驱动执行，是控制器启动后调用的主逻辑单元。适合编排调用链、状态机主循环。**调用约束：PRG 可调用 FUN、FB 和 PRG**。

**选择标准**：按工艺或功能将工程分段。反复调用的程序段封装为 FB；纯算法封装为 FUN；顶层编排逻辑放入 PRG。

**命名规范**：POU 名称前加统一前缀 — `PRG_`（程序）、`FB_`（功能块）、`FC_` / `FUN_` / `FUNC_`（函数）、`GlobVar_`（全局变量列表）。不同功能部分用下划线分割。POU 名不能包含空格，不能与其他 POU 或数据类型重名。

## A1 — 书中的应用（Past Application）

### 案例 1: 交通灯信号控制 — SFC + FB 模块化拆分
- **问题**: 一个交通灯控制系统需要处理东西/南北方向共 6 个信号灯的多阶段时序切换（绿灯 20s/10s、黄灯 3s、红灯等待），若全部写在一个 POU 中会难以维护。
- **方法论的使用**: 使用 SFC 编写主控 PRG（TRAFFIC_MAIN），拆出两个功能块 — `FB_TRAFFICSIGNAL` 根据 STATUS 值输出灯状态（封装信号分配逻辑）和 `FB_WAIT` 封装 TP 定时器延时逻辑。主程序中创建 `LIGHT1`、`LIGHT2` 和 `DELAY` 三个 FB 实例分别控制东西/南北方向灯的时序。
- **结果**: 逻辑清晰分层，信号分配和定时器逻辑可独立测试和复用。

### 案例 2: 恒压变频供水 — 功能块封装复用
- **问题**: 恒压供水系统中两台水泵需要工频/变频切换逻辑、PID 调节、手动/自动双模式，程序量大且两种水泵逻辑相似。
- **方法论的使用**: 将水泵控制逻辑封装为 `FB_PumpControl` 功能块，包含变频器频率到达信号检测、切换保护定时器、工频/变频输出等内部状态逻辑。主程序 `PRG_WaterSupply` 创建两个功能块实例分别控制 1# 泵和 2# 泵。
- **结果**: 避免了重复编码，单个功能块调试通过后两个实例都可正常工作，扩展第 3 台泵只需新增一个实例。

## A2 — 触发场景（Future Trigger）★

### 用户会在什么情境下需要这个 skill?

1. 设计新项目时，需要决定一段逻辑应该写成函数（FUN）、功能块（FB）还是程序（PRG）
2. 重构遗留代码时，发现一个 PRG 中有大量重复代码段，需要识别哪些可以封装为 FB 进行复用
3. 团队评审 POU 命名规范时，需要统一 `PRG_` / `FB_` / `FC_` 前缀的使用规则
4. 编译报错"function cannot call function block"，需要理解调用约束并修正
5. 需要将一个 FB 升级为可继承的基类，用 EXTENDS 派生子功能块

### 语言信号
- "这个逻辑要不要写成功能块"
- "函数和功能块有什么区别"
- "我这个功能块编译报了错"
- "怎么组织我的程序结构"
- "FB 要实例化是什么意思"
- "POU 命名有什么规范"

## E — 可执行步骤（Execution）

1. **识别逻辑类型，选择 POU 类型**
   - 判断逻辑是否有内部状态需要记忆（定时器累计值、运行模式、计数等）？
     - 有状态 -> **功能块（FB）**
     - 无状态、纯算法/转换 -> **函数（FUN）**
   - 判断是否为顶层入口/编排逻辑？
     - 是 -> **程序（PRG）**
   - 完成标准：每段逻辑被分配了明确的 POU 类型归属

2. **遵循调用约束，设计调用链**
   - FUN -> 只能调用 FUN
   - FB -> 可调用 FUN 和 FB
   - PRG -> 可调用 FUN、FB 和 PRG
   - **禁止**：FUN 内部调用 FB 实例；任何 POU 直接或间接调用自身（递归）
   - 完成标准：调用链从顶向下检查，无违反调用约束的情况

3. **统一命名，添加前缀**
   - 程序：`PRG_` + 含义（如 `PRG_TrafficMain`）
   - 功能块：`FB_` + 含义（如 `FB_PumpControl`）
   - 函数：`FC_` / `FUN_` + 含义（如 `FC_ScaleConversion`）
   - 全局变量列表：`GlobVar_` + 含义
   - 完成标准：项目内所有 POU 和 GVL 均遵循前缀命名规范

4. **实例化与复用设计**
   - FB 在声明区用 `VAR fbInstance : FB_MyBlock; END_VAR` 实例化
   - 同一逻辑被多处调用/多个对象需要 -> **一个 FB 定义 + 多个实例**
   - 纯算法、无状态 -> **FUN**
   - 完成标准：FB 实例化数量合理，无重复定义的冗余逻辑

5. **确认无硬件耦合**
   - 功能块和函数的局部变量中**不允许**出现 `%I` / `%Q` 等固定地址（AT 声明）
   - 硬件地址只在 PRG 层或全局变量列表中映射
   - 完成标准：所有 FB/FUN 可在不同硬件平台间移植编译

## B — 边界（Boundary）★

### 不要在以下情况使用此 skill
- 用户只需要具体语言的语法写法（如 ST 的 CASE 语句），应使用 **codesys-st-language** skill
- 用户询问变量类型声明、匈牙利命名法前缀表（如 b/bool, i/INT），应使用 **codesys-variable-system** skill
- 变量命名涉及持续变量（RETAIN / PERSISTENT）的特定规则，属于变量声明体系而非 POU 设计范畴
- 用户询问任务配置（周期/优先级/看门狗），不属于 POU 设计问题
- 用户项目只需要一个简单 PLC_PRG 就能完成的小程序，过度分层会增加理解成本
