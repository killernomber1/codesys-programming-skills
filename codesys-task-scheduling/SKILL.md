# 任务调度与实时性配置

## R — 原文（Reading）

> "CoDeSys 中的任务优先级可设 32 个级别（0 到 31，0 最高）。高优先级任务能中断较低优先级的程序执行。"
>
> — 陆国君，《CODESYS 基础编程及应用指南》

---

## I — 方法论骨架（Interpretation）

CoDeSys 的任务系统是连接"硬件循环"与"应用程序执行"的桥梁，核心围绕四个维度展开：

**1. 四种任务类型及其选型优先级**

| 类型 | 英文 | 触发机制 | 实时性 | 推荐度 |
|------|------|---------|--------|-------|
| 固定周期循环 | Cyclic | 定时器恒定时基触发 | 确定 | 首选 |
| 自由运行 | Freewheeling | 执行完毕立即重启 | 不确定 | 尽量少用 |
| 事件触发 | Event | 指定变量上升沿 | 取决于采样频率 | 特殊场景 |
| 状态触发 | Status | 指定变量为 TRUE | 取决于电平持续时间 | 特殊场景 |

**关键区别**：事件检测上升沿（信号刚变为 TRUE 时触发一次），状态检测电平（变量为 TRUE 的整个期间持续触发）。若采样频率过低而脉冲过窄，事件触发可能完全丢失信号。

**2. 32 级优先级（0 最高 / 31 最低）**：高优先级任务可中断低优先级任务立即执行。**禁止分配相同优先级**给两个任务，否则 CPU 调度顺序不确定，程序行为不可预测。通信任务通常配置较高优先级（如 0-3）和较短循环时间。

**3. 看门狗配置**：每个任务可配置独立看门狗。触发时间 = 时间参数 × 灵敏度。核心不等式：
```
看门狗触发时间 > 固定周期循环时间 > 程序最大循环时间
```
- 若循环时间 > 周期时间：CPU 检测到超出计数，影响实时性但继续执行。
- 若循环时间 > 看门狗时间：看门狗触发，CPU 停止程序执行（进入 STOP）。

**4. 多子程序调用**：两种方式 —— (A) 在任务配置中按序添加子程序，自动顺序调用；(B) 在 PLC_PRG 或主程序中通过代码调用各子程序，支持 IF/CASE 条件分支。方式 B 更灵活，为推荐做法。执行顺序遵循调用链深度优先（最深层嵌套的子程序最先执行）。

## A1 — 书中的应用（Past Application）

### 案例 1: 高速运动控制任务配置
- **问题**: 三轴伺服系统中，插补周期设定为 10ms，但轴位置存在明显跟踪误差和速度抖动，尤其在多轴联动时更为严重。
- **方法论的使用**: 分析任务配置后发现运动控制任务与 HMI 通信任务被分配到相同优先级（优先级 10）。根据规则，将运动控制任务提升至优先级 1，HMI 通信降至优先级 8。运动控制任务采用固定周期循环、周期设为 2ms；HMI 任务同设为固定周期循环、周期 50ms。为运动控制任务配置独立看门狗（时间 5ms × 灵敏度 2 = 10ms 触发）。
- **结果**: 轴跟踪误差从 0.5mm 降至 0.02mm，速度曲线平滑，看门狗未触发。任务监视器显示最大循环时间 1.8ms < 周期 2ms < 看门狗 10ms，不等式成立。

### 案例 2: 自由运行任务导致的通信超时
- **问题**: Modbus TCP 通信频繁超时，PLC 周期性进入 STOP 模式，看门狗日志显示 Watchdog timeout。
- **方法论的使用**: 分析任务监视器发现，Modbus 处理任务使用自由运行（Freewheeling）模式，某次通信阻塞导致该任务循环时间飙升至 500ms，远超看门狗设定值 200ms。将任务切换到固定周期循环（Cyclic 50ms），并分离通信逻辑与主控逻辑为两个独立任务，通信任务优先级设为 3（高于主控任务的优先级 8）。
- **结果**: 通信超时消除，任务循环时间稳定在 30-45ms 之间，看门狗再未触发。

### 案例 3: 多子程序调度方式选型
- **问题**: 一个恒压供水项目需根据手动/自动模式执行不同的控制流程，所有子程序在任务配置中添加后按固定顺序执行，无法根据模式切换。
- **方法论的使用**: 采用"主程序调用"方式（方式 B），在 PLC_PRG 中使用 IF bAutoMode THEN ... ELSE ... 条件分支，手动模式和自动模式分别调用不同的子程序序列。同时将急停检测作为独立事件触发任务，不经过主程序调用链。
- **结果**: 代码结构清晰，手动/自动模式切换平滑，急停响应时间 < 1ms。

## A2 — 触发场景（Future Trigger）

### 用户会在什么情境下需要这个 skill?

1. **新项目任务规划**：用户新建 CoDeSys 工程后，需要决定添加哪些任务、分配什么优先级、选择哪种任务类型。信号词："新建任务"、"添加循环任务"、"任务类型选哪个"。

2. **实时性故障排查（死机/看门狗/抖动）**：PLC 周期性进入 STOP、程序无响应、任务监视器显示循环时间异常。信号词："看门狗触发"、"任务超时"、"STOP 模式"、"程序跑飞"。

3. **多任务执行顺序与优先级调整**：多个程序模块（通信/运动/逻辑/显示）需合理分配优先级和周期，避免低优先级任务饿死或高优先级任务过度占用 CPU。信号词："优先级分配"、"任务中断"、"通信任务优先级"、"任务时序"。

4. **程序结构重构（从单任务到多任务）**：当程序规模扩大，单个任务已无法满足实时性要求，需将功能拆分为多个任务。信号词："程序拆分"、"分任务"、"子程序调用"、"多任务架构"。

### 语言信号
- "任务怎么配" / "看门狗溢出了" / "优先级设多少" / "Cyclic 和 Freewheeling 区别" / "事件触发和状态触发" / "多子程序调用" / "任务监视器"

## E — 可执行步骤（Execution）

1. **任务类型选择与命名**
   - 根据功能需求选择任务类型：基础逻辑/通信/运动控制 → 固定周期循环；急停/硬件中断 → 事件触发；状态指示灯/报警扫描 → 状态触发；临时测试程序 → 自由运行。
   - 推荐命名规范：Task_Motion_1ms、Task_Logic_20ms、Task_Comm_50ms（体现功能和周期）。
   - 完成标准: 每个任务有明确的功能定位和类型选择依据，无"默认未配置"状态的任务。

2. **优先级分配与冲突检查**
   - 列出所有任务的实时性要求，按重要性排序。最高实时性要求（如运动控制/急停）分配优先级 0-3；通信任务分配 3-8；逻辑控制分配 8-15；HMI/显示任务分配 15-31。
   - 逐项检查：是否有两个任务分配了相同优先级？有则立即调整（升或降一级）。
   - 完成标准: 所有任务优先级在 0-31 范围内独占、不重复，且高优先级任务均为真正需要快速响应的功能。

3. **看门狗参数计算与设定**
   - 对于每个固定周期循环任务，先通过经验或估算确定"程序最大循环时间"。
   - 设定"固定周期循环时间" = 程序最大循环时间 × 1.5（预留 50% 余量）。
   - 设定"看门狗触发时间" = 固定周期循环时间 × 2（预留 100% 余量），再除以灵敏度系数算出具体"时间"参数。
   - 验证不等式：看门狗触发时间 > 固定周期循环时间 > 程序最大循环时间。
   - 完成标准: 每个任务的三个时间参数满足严格不等式，且看门狗触发时间不超过业务可容忍的最大响应时间。

4. **子程序调用方式设计**
   - 评估程序是否需要在不同条件下执行不同子程序路径：若否，用任务配置添加（方式 A）；若是，用主程序 IF/CASE 分支调用（方式 B）。
   - 方式 B 时，确保 PLC_PRG 中的调用链符合深度优先执行顺序：子程序 → 子程序的子程序 → 返回。
   - 完成标准: 任务配置中的程序和主程序调用链无遗漏，执行顺序满足工艺要求。

5. **在线验证与优化**
   - 登录 PLC 后打开任务监视器，观察每个任务的平均/最大/最小循环时间。
   - 若最大循环时间接近或超过固定周期时间：优化代码缩短执行时间，或增大周期值。
   - 若最大循环时间接近看门狗触发时间：立即增大看门狗参数，并排查瓶颈 POU。
   - 记录稳定运行后的基准值，作为后续维护参考。
   - 完成标准: 所有任务在满负荷工况下满足不等式，任务监视器无周期性报警，PLC 连续运行 7 天不触发看门狗。

## B — 边界（Boundary）

### 不要在以下情况使用此 skill
- **纯仿真/离线开发阶段**：在程序逻辑未完成前，过早优化任务配置和优先级意义不大。应先在单任务中完成功能验证，再做多任务拆分。
- **单任务小程序**：程序总代码量小于 100 行，一个固定周期循环任务即可满足所有需求时，无需创建多个任务。
- **POU 内部逻辑调试**：任务配置解决的是"谁先执行、何时执行"的问题，而非"POU 内部逻辑是否正确"。代码层面的变量/逻辑错误应使用断点和在线监控排查。
- **单次循环排除**：如果问题仅在程序第一次循环时出现（如变量初始化时序），应检查启动行为和变量初始值，而非调整任务优先级。
